# step-verify

목적: "완료했습니다"를 증거로 바꾸고, 그 자리에서 기록과 커밋까지 끝낸다. 검증·기록·커밋은 한 묶음이다.

## 1. 검증
1. 이번 단계가 PROBLEM.md의 어느 성공 기준과 관련되는지 한 줄로 적는다.
2. **직접 실행**: 실제 데이터로 실행하고 핵심 출력(건수, 합계, 샘플 3행)을 보여 준다.
3. **깨질 수 있는 입력** 3~5개(빈 입력, 경계값, 자정 넘김, 형식 오류, 특수값, 예외 그룹)를 테스트로 작성해 실행한다. 테스트를 통과시키려고 테스트를 약하게 고치지 않는다.
4. 실패하면 원인을 한 줄로 설명하고 고친다 → DECISIONS.md에 `(수정)` 행.
5. 성공 기준 수치와 대조한다(예: 목표 100건 이하 → 현재 87건).

## 2. 문서 갱신
- VERIFY.md에 한 행 추가.
- 새 구성(파일·함수)이 생겼거나 구조가 바뀌었으면 COMPONENTS.md 구성표 갱신(책임 한 문장, 입력→출력, 따로 둔 이유, 깨지면, 구조 결정자).

## 3. 챌린지 기록 (해당할 때만)
이번 단계에 아래가 있었으면 CHALLENGES.md에 한 건 추가한다:
이상한 수치 발견 / 테스트 실패·버그 수정 / AI 제안·코드를 사람이 거절하거나 고침 / 현업 답변으로 방향 전환 / 과한 설계 축소.
- 칸: 상황 / 문제 인식(어떻게 알았나) / 원인 가설 / **사용자가 AI에게 보낸 지시 원문** / AI 결과 / 사람의 판단·수정 / 검증(명령 → 수치) / 결과(전 → 후) / 증거(커밋·DECISIONS·VERIFY) / 배운 것
- 지시 원문은 이번 세션의 사용자 메시지를 **그대로** 인용한다. 사람이 한 판단과 AI가 한 일을 구분해서 쓴다.

## 4. 커밋 (GIT.md 형식)
1. `git status --short` → 이번 단계 파일만 `git add`. `git diff --staged --stat`와 `git diff --staged`를 읽는다.
2. staged diff에 `api_key`, `token`, `password`, `secret`, `sk-`, `.env`가 있으면 멈추고 알린다.
3. 메시지를 `.git/COMMIT_MSG_DRAFT`에 쓰고 `git commit -F .git/COMMIT_MSG_DRAFT`:
   ```
   feat|fix|test|refactor: <무엇, 50자 이내> — 성공기준 #n

   - 변경: ...
   - 검증: <명령> → <결과>
   - 결정: <DECISIONS 항목, 있으면>
   ```
   diff에 없는 내용은 쓰지 않는다. 실행하지 않은 검증은 `검증: 미실행 (이유)`.
4. 금지: `--amend`, `rebase`, `push --force`, `reset --hard`, `--no-verify`, 승인 없는 push.

## 보고 (5줄 이내)
- 실행한 명령과 핵심 결과 / 추가한 테스트와 통과 여부
- 성공 기준 대비 현황
- 기록한 챌린지(있으면) / 커밋 해시와 제목
- 남은 위험 1개

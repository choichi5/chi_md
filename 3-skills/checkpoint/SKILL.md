# checkpoint

목적: 두 가지를 한 번에 점검한다. ① AI가 만든 범용적이고 과한 설계를 요구 크기로 깎는다(오버엔지니어링은 감점). ② 지금 끝나도 내가 구성·선택·챌린지를 설명할 수 있는지 확인한다.

## A. 범위 점검
1. PROBLEM.md의 성공 기준, 사용자, 실행 환경을 읽는다.
2. 코드의 주요 기능·모듈을 나열하고 각각을 성공 기준 번호에 연결한다.
3. 어디에도 연결되지 않거나 필요 이상인 것을 표시한다. 예: 요구에 없는 보안·무결성 장치(해시, 서명), 한 번 쓰는 기능의 설정·플러그인 구조, 환경에 비해 무거운 의존성(서버, DB), 요구보다 넓은 입력 지원.
4. 표로 보고: `기능 | 연결된 성공 기준 | 판정(유지/축소/제거) | 이유`
5. **삭제는 사용자 승인 후에만.** 승인되면 제거 → DECISIONS.md에 "범위 축소: X — 이유" → CHALLENGES.md에 한 건 → GIT.md 형식으로 `refactor:` 커밋.
6. 성공 기준인데 아직 구현되지 않은 것이 있으면 함께 알린다.

## B. 설명 준비 점검
1. COMPONENTS.md 구성표를 실제 코드(파일·함수 이름, 입력·출력)와 대조해 틀린 칸을 고친다.
2. 아래가 비어 있으면 **사용자에게 질문**한다(대신 지어내지 않는다):
   - 각 구성의 책임 한 문장, 구조를 누가 정했나
   - 핵심 방법(알고리즘·모델)을 왜 골랐나, 비교한 대안과 수치 → 없으면 `choice-compare` 실행을 제안
   - CHALLENGES 기록이 2건 이상 있나, 지시 원문이 들어 있나
3. 지금 상태로 30초 설명을 만들어 보여 준다: "이 도구는 <누구>의 <문제>를 해결합니다. 흐름은 <단계> → <단계> → <단계>이고, 핵심 방법은 <방법>(<비교 근거>)입니다."
